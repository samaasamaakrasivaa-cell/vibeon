# CD-01: самостоятельная публикация VibeOn

Согласованная задача включает реализацию, проверки, merge и результат на сайте. Tech Lead сопровождает весь процесс; техническое переключение выполняет существующий GitHub CI через SSH_KEY / SSH_HOST. Установка Codex на MacBook не является условием серверной выкладки. Новые API-ключи и платные сервисы не добавляются.

## Обычный выпуск

1. Готовый PR проходит предметное ревью, проверку типов и сборку. Отдельная репетиция проверяет копирование, неуспешный запуск и совместимый откат на синтетической БД и файлах.
2. После merge в main CI собирает один образ с полным source SHA и recipe SHA, проверяет его на изолированной БД, сверяет runtime-версию и метку для браузера. PR не запускает серверный этап.
3. При включённом enabled в deploy/release-policy.json драйвер сверяет актуальную main, текущее приложение, проверенную топологию и совместимый образ отката. Устаревший или неизвестный источник блокируется до изменения сайта.
4. На сервер передаётся именно проверенный образ. Все серверные workflow используют группу server; исполнитель и служебные команды используют одну файловую блокировку.
5. Приложение кратко останавливается для согласованного дампа БД и архива uploads, затем прежняя версия возобновляет работу. Восстановление пары проверяется в отдельных временных томах PostgreSQL с отключённой сетью. Рабочие записи, копии и .env остаются только на сервере.
6. После успешных проверок переключается приложение. Image ID и полный SHA подтверждаются внутри контейнера и через публичный /api/health. При неудаче запускается заранее проверенный совместимый образ с актуальными томами. Новые ответы старым дампом не заменяются.
7. Tech Lead подтверждает результат и обновляет статус задачи. Ответ SSH с неизвестным результатом, зелёная сборка без release или один HTTP 200 не считаются публикацией.

## Существующий общий Caddy

Read-only проверка подтвердила подключённый через прежний attach-proxy.sh общий Caddy. Политика закрепляет точный digest его образа. Допуск дополнительно требует ожидаемую команду caddy run, отсутствие известных DB-переменных, ограниченные mounts конфигурации и отсутствие доступа к томам VibeOn. Текущие контейнеры связываются между наблюдением и исполнителем хешем идентификаторов; неизвестный сосед остаётся блокером. Общий Caddy не останавливается и не обновляется при выпуске приложения.

## Версия в браузере и служебные команды

BUILD_STAMP равен полному source SHA, APP_VERSION передаётся в runtime. Существующий UpdateNotice предлагает обновить открытую вкладку после смены сборки. Кнопка обновляет вкладку; публикацию выполняет CI.

Перед первым переключением устанавливаются два проверенных служебных скрипта. Их прежние хеши проверяются до любой записи, старое содержимое сохраняется на сервере. Перезапуск и настройки учитывают release-image.json и файловую блокировку. Старые Server update/install и vibeon.sh update выведены из эксплуатации, прежние образы не удаляются. При будущей инфраструктурной правке helpers ожидаемые исходные хеши в политике обновляются в том же проверенном PR.

## Границы автоматического механизма

Автоматический выпуск поддерживает текущую единственную реплику приложения и БД, обычные локальные Docker volumes и одинаковую схему/историю миграций у текущего приложения, кандидата и отката. Новая схема требует отдельной технической реализации перехода; обычное разрешение на публикацию не превращается в разрешение на потерю данных или массовый пересчёт истории.

Резервная копия на том же сервере обеспечивает проверку и восстановление для выпуска, но сама по себе не является копией на другом сервере. Рабочие данные не отправляются в публичные артефакты GitHub. Новые расходы или перенос данных требуют отдельного решения.

Сигналы завершения обрабатываются с возвратом приложения. После SIGKILL, потери питания или неоднозначного результата состояние сначала исследуется по локальному журналу; следующий выпуск блокируется до восстановления. Агент отвечает за устранение технической причины, а не за повторное получение уже выданного разрешения на обычную публикацию.

### Свободное место перед переносом образа

Задание публикации на `main` использует существующую группу GitHub Actions `server`. Тот же серверный файл `.release.lock` защищает повторный замер и импорт образов, а затем отдельно защищает установку служебных файлов, смену версии и очистку. На каждом этапе сверяется текущая версия и точный ID образа. Повтор запуска для уже работающего SHA заканчивается без нового импорта.

До записи на сервер исполнитель измеряет БД одним запросом только на чтение и суммарный размер файлов тома VibeOn. Имена и содержимое файлов в CI не передаются. Для образов, которые уже доступны под точным ID, передача пропускается. Для остальных исполнитель формирует один временный архив в CI и учитывает размер его слоёв после распаковки. Перед импортом проверяются свободные байты и inode каталога копий, хранилищ Docker и временного каталога. На общем разделе потребности учитываются вместе. Расчёт включает полную копию и проверку восстановления, 512 МиБ запаса для системы, предыдущие полные пары многоэтапного выпуска и консервативный резерв импорта до трёх размеров измеренного архива. Существующая проверка непосредственно перед созданием копии также действует.

При нехватке места CI выдаёт `insufficient_pretransfer_space` и публикует только числовые пределы в `storage_capacity`. Не повторяйте выпуск, пока свежий замер не подтвердит запас. Дефицит разбирается в [#67](https://github.com/samaasamaakrasivaa-cell/vibeon/issues/67). Предупреждение на успешном запуске означает, что запас сверх расчётного порога упал ниже 512 МиБ. Сокращать обязательную копию или подменять размер архива значением `docker image inspect .Size` для обхода порога нельзя.

После успешного выпуска исполнитель может убрать свои служебные файлы в строго известных каталогах `/tmp/vibeon-delivery.*`. Проверка требует маркер происхождения, владельца root, права каталога, разрешённые имена и отсутствие ссылок или перехода в другую файловую систему. Каталоги завершившихся штатно операций удаляются после каждого запуска. Помеченные остатки после прерывания можно убрать при успешной публикации спустя 24 часа. Общий кэш Docker и файлы других проектов не участвуют в очистке.

Порог в 4096 свободных inode дополняет проверку байтов. После импорта и перед сменой приложения запас проверяется заново. При ошибке импорта или выпуска список `storage_import_candidates` указывает возможные остатки, требующие сверки с журналом. Автоматическая очистка не удаляет образ с неподтверждённым владельцем или ссылками.
