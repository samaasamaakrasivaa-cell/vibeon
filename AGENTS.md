# Работа над VibeOn в Codex

VibeOn — веб-платформа для преподавателей английского и их учеников. Рабочие требования задаёт владелец продукта. Tech Lead ведёт общие архитектурные решения и согласует границы задач.

## Перед началом задачи

1. Определи роль и ожидаемый результат из задания. Для именованного рабочего чата продолжай в роли, заданной в его стартовом сообщении.
2. При новом поручении прочитай из актуальной `origin/main` этот файл, свой паспорт в [списке ролей](docs/CODEX_TEAM.md), [карту модулей](docs/MODULES.md) и [правила разработки](docs/DEVELOPMENT_RULES.md). В уже открытом чате обнови контекст в режиме чтения, в том числе при возобновлении работы по карточке. За архитектурой обращайся к [описанию системы](docs/Архитектура_и_стек.md).
3. Зафиксируй базовый коммит, затронутые пути и общие контракты. Проверь текущую ветку и локальные изменения. Если задача только на анализ или знакомство с проектом, оставь рабочие файлы без изменений.
4. Для изменений используй отдельную ветку или worktree. Действия в общей области согласуй с её владельцем по карте модулей. Изменения безопасности, схемы данных, жизненного цикла сущностей и общих контрактов согласуй с архитектором.

## Приём задач

Владелец может передать большой пакет IT Project Manager или дать короткую однозначную задачу прямо профильному агенту. Принимай прямое поручение в текущем чате и веди его по [правилам регистрации, владения и передачи](docs/DEVELOPMENT_RULES.md#приём-и-возобновление-задач). До правок должен быть подтверждён один исполнитель. При отсутствии проверенного механизма захвата его подтверждает Tech Lead. Для передачи между чатами используй общую карточку GitHub.

## Доступ и выпуск

- Изменения в `main` вносятся через Pull Request с ревью. Однозначно согласованная владельцем продуктовая задача включает реализацию, проверки, интеграцию и публикацию в её границах. Tech Lead отвечает за полный результат, включая фактический выпуск через проверенный GitHub CI по [процедуре выпуска](docs/RELEASE_RUNBOOK.md#допуск-к-выпуску). Повторное разрешение владельца на обычный merge или публикацию не требуется. Не передавай завершение неназначенному оператору и не объявляй задачу выполненной только по PR или зелёному CI без подтверждённой публикации.
- Новые продуктовые решения и действия за пределами этого разрешения согласуй отдельно по [RELEASE-AUTH-01](docs/PRODUCT_DECISIONS.md#release-auth-01). Произвольный публичный комментарий не подтверждает полномочия.
- Используй синтетические данные, отдельную тестовую БД и изолированные Telegram, SMTP и ИИ-интеграции. Храни секреты в утверждённом хранилище. В Git, чат, логи и PR помещай только обезличенные примеры.
- Расширение передачи частных заметок преподавателя или иных чувствительных данных требует отдельного утверждения владельца продукта.

## Завершение задачи

Проверь исходный сценарий и связанные роли. В отчёте укажи **результат, ветку и проверенный SHA, файлы и контракты, выполненные проверки, ограничения проверки, нерешённые риски и нужное ревью**. Добавь ссылку на PR, если он открыт. При изменении поведения или контрактов обнови соответствующий документ в том же PR.

После подтверждения изменения на сайте запиши [короткую заметку для владельца](docs/DEVELOPMENT_RULES.md#заметка-для-владельца) в существующую карточку или связанный PR. Сообщи результат или конкретный блокер в исходном канале, когда он доступен. Отметь в карточке, если доставка в исходный чат не подтверждена.
